# 08｜整链延迟：程序等待与运行环境

测量：2026-10-11 至 2026-10-12。正式源码为 `aa94289`，验收日志补交至 `4d02ed6`。Ubuntu 26.04 / VMware，Release，计时日志模式 1，逐记录 fsync。服务器允许使用 CPU 0–3，负载发生器使用 CPU 4；不是独占物理核心。

**结论：程序存在同步持久化和接收阻塞回报的成本，运行环境又会放大这些成本。已观察到明显的存储等待波动及后台索引干扰；没有证据证明电脑硬件性能永久下降，也没有证明队列和对象池优化导致了此前约 3% 的中位数回归。**

## 1. 测试时发现了什么问题

组件测量的节省是几十纳秒，真实订单回报却需要数毫秒；过载时还会积压到秒级。这次先保留正式源码，再分两种实验检查：

- **诊断窗口**：旧版与发送刷新版都加入相同的审计分段计时，正常负载 6 轮、过载 4 轮。用于找时间花在哪里，不作为正式提速成绩。
- **环境窗口**：正式二进制与一个回报推进候选交替测 12 轮，并采样 Windows 性能计数器。出现极大波动，随后用同一个正式二进制做索引运行／冻结／恢复 6 轮对照。

每轮固定 4 客户、8 品种、128 条闭环预热、256 条正式请求，输入种子 20260928。正常负载 50/s，短时过载 500/s；NEW/CANCEL 不发生撮合成交。超时、失败与慢轮全部保留，不能拿这组实验代表生产成交吞吐。

## 2. 怎样定位原因

### 2.1 正常负载：主要在等三次持久化

源码：[CriticalJournal](../../common/critical_journal.h)、[MatchingEngine](../../exchange/matcher/matching_engine.h)、[OrderServer](../../exchange/order_server/order_server.h)。

普通请求依次经过 RECEIVED → APPLY → RESPONSE，每条记录都在同一把互斥锁内执行 write 和 fsync。回报在 RESPONSE 持久化之后才进入后续发送过程。

诊断只在内存中保存固定字段，预留 8,192 个槽；程序退出、业务线程结束后再写 CSV。没有为每个计时点增加磁盘日志，也没有取消 fsync。客户端与诊断均使用同一虚拟机的单调时钟，按客户、订单和 NEW/CANCEL 类型关联；所有 2,560 条正式请求都成功关联，逐笔分段相加严格等于该笔整链时间。

正常负载六轮中，每笔三次 fsync **合计耗时的 P50** 为 7.17–8.35 ms，整链 P50 为 8.31–9.51 ms。等审计锁的 P50 只有约 0.0006 ms；因此换自旋锁解决不了典型请求的大头。

一次最慢请求耗时 81.02 ms：三次 fsync 占 40.50 ms，持久回报完成之后又等了 39.98 ms。不能把所有尾延迟都归到落盘。

分段统计不能随意相加中位数。以第 0 轮旧版为例，整链**均值**为 9.304 ms，其中 fsync 均值 8.054 ms，占约 86.6%；这是同一批逐笔数据计算出的比例。线程实际 CPU 时间另行记录，不能把墙钟等待当成 CPU 运算，也不能仅用“墙钟减 CPU”判断究竟是磁盘还是调度器。

### 2.2 为何同轮新版中位数可能反而更高

第 1 组正常负载中，旧版 P50 为 9.204 ms，刷新版为 9.508 ms，增加 0.304 ms；相应的三次 fsync 合计 P50 从 8.032 变为 8.353 ms，增加 0.321 ms。这支持持久化等待波动掩盖局部收益的解释，但两个中位数的差接近，不等于完整因果证明。

更强的环境证据来自后续未插桩测量：**正式二进制 SHA-256 始终为 `f94347fa59bcda6aa2a87edbec88f3382ff1b28c88fa3131e106393b22ab4c94`，相同 50/s 输入的 P50 却先后出现 973.535 ms 和 37.574 ms。首次预热还超时。** 代码没有变，这种运行间差额不能解释成一次算法修改的回归。

### 2.3 过载：多数时间已经变成排队

500/s 的发送间隔约 2 ms，但每笔请求需要三次串行持久化。诊断中，这三次 fsync 合计 P50 仍有约 5.93–7.59 ms。因此输入速度超过了这条串行路径当时能持续处理的速度，后来的请求只能排队；不能靠节省几十纳秒补齐这个差额。

四轮过载中，“RECEIVED 完成 → 开始 APPLY”的 P50 为 726.58–988.09 ms。这个综合区间包含定序暂存、请求队列和调度，尚未继续拆成三个独立时间，不能直接全部称为队列本身的访问成本。APPLY 完成到 RESPONSE 开始的片段 P50 仍约 0.07 ms，也不代表所有订单类型的完整撮合耗时。

### 2.4 已持久化的回报，还会被接收回调挡住

`OrderServer::run()` 先调用 `sendAndRecv()`，返回后才消费回报队列。接收回调可以连续处理多帧，每帧又可能等审计落盘。即使另一笔回报已经完成，也会等接收回调退出。

前述 39.98 ms 的回报后等待中，有 39.44 ms 与其他 RECEIVED 审计调用区间重叠。过载时，正式刷新版还有一笔回报后等待 378.36 ms，其中 362.78 ms 与其他 RECEIVED 调用重叠。时间重叠结合单线程调用位置，支持接收阻塞回报的判断；它不是对内核调度、TCP 传输各自耗时的完整拆分。

record/07 的立即刷新修复了“回报已入 TCP 缓冲，还要等下一轮发送”，但没有解决“回报还在队列中，消费线程正在接收回调里等待”。这是两个位置不同的问题。

### 2.5 是本机性能下降，还是程序的原因

同一正式二进制、同一 50/s 输入，仅临时冻结虚拟机的 `localsearch-3.service`，得到：

| 索引状态 | 第 1 轮 P50 | 第 2 轮 P50 |
|---|---:|---:|
| 运行 | 2,231.610 ms | 1,506.009 ms |
| 临时冻结 | 80.818 ms | 232.464 ms |
| 恢复运行 | 976.207 ms | 854.671 ms |

六轮业务核对都通过。冻结期间明显改善、恢复后再次变慢，支持后台索引参与干扰；但冻结后仍明显慢于早先窗口，而且各轮持续波动，所以不能说它是唯一原因。实验结束已恢复服务，未永久停用任何后台服务。

再停止交易进程，单独向同一测量路径执行 256 次 128 字节 write + fsync：

| 索引状态 | P50 | P99 | 最大值 |
|---|---:|---:|---:|
| 运行 | 1.819 ms | 83.247 ms | 165.832 ms |
| 冻结 | 2.059 ms | 41.326 ms | 53.231 ms |
| 恢复 | 1.157 ms | 8.761 ms | 13.945 ms |

**交易程序没有运行，存储同步仍有大幅波动。** 恢复后的独立存储测试反而最好，进一步说明不能简单归因于一个索引开关。这个小测试不是 SSD 极限性能测试，也无法单独区分虚拟磁盘、宿主文件系统、真实磁盘及 vCPU 调度。

Windows 在候选对照窗口记录了 213 个样本：总体 CPU 中位数约 18.7%、样本最大约 55.9%，可用内存约 4.88–6.43 GiB；磁盘平均写服务时间的采样值最高约 75.8 ms，并有硬缺页读入活动。虚拟机抽样时 swap 使用为 0，可用内存约 5.7 GiB，但 I/O pressure 明显。总体 CPU 没跑满不能排除单核或虚拟机调度等待；硬缺页也可能来自文件映射，不能直接解释成内存不够。

当前电源方案为“平衡”。这些数据没有历史同条件基准，没有温度、功耗限制或宿主磁盘逐请求跟踪，因此**不能认定硬件老化、CPU 降频故障或 SSD 损坏**。现在证据支持的是：运行环境有可见波动，程序的同步 I/O 和串行接收路径会把它放大成整链等待。

## 3. 尝试了什么改法

在独立候选副本中，把已有回报消费代码提取为 `drainResponses()`，接收下一帧之前先推进已完成的回报：

```cpp
// 修改前：整个接收过程返回后才消费回报。
tcp_server_.sendAndRecv();
// ...原有回报队列消费和 flushSend...
```

```cpp
// 候选：保留循环末尾推进，同时在每帧处理前增加推进机会。
tcp_server_.sendAndRecv();
drainResponses();

// recvCallback 内：
while (还有完整请求帧) {
    drainResponses();
    // ...原有校验、审计和定序暂存...
}
```

以上为流程示意；[完整候选补丁](experiments/response-candidate.patch)保留准确源码差异。没有更改 FIFO 发布边界，没有增加线程，也没有把未持久化的回报提前发送。发送缓冲满时仍保留队首，入缓冲成功才推进回报序号。

**候选尚未进入正式源码。** 正确性检查通过，但性能对照受严重环境波动影响，既有快轮也有极慢轮。当前不能将它称为已验证的整链提速，也不新增自旋锁或通用异步任务线程。

## 4. 重新测试和当前边界

- 审计诊断 10/10 轮通过业务核对，正式请求 2,560 条均成功关联。
- 未插桩候选对照 11/12 轮通过；失败轮是正式基线预热未完成，不作成功样本或速度成绩。
- 索引运行／冻结／恢复对照 6/6 轮通过；三阶段都保留原始证据。
- 候选完整 CTest：26/26 通过。
- 新确定性反例：旧版会把现成回报留到回调结束，测试失败；候选通过。还验证了发送缓冲满时不提前弹出、重试后序号连续、请求 FIFO 与会话不变。这个小测试覆盖回调与缓冲语义；真实网络仍由其他回归及整链压测覆盖。

没有将候选变为默认版本，也没有重新宣称 record/07 的全链路性能已验收。下一步应先固定运行环境和诊断日志负载，再对接收期间推进回报做交替复测；若要减少 fsync 次数，需单独设计批量持久化及提交水位，保持“持久化完成后才能确认”的契约，不能简单丢给后台线程就返回成功。
