# 07｜组件变快后，为什么整条链不一定变快

测量日期：2026-10-11。基线为 `995bdca` 加已有 record/06 工作区修改；测量时修复尚未提交；现已收录于 `aa94289`，验收日志补交于 `4d02ed6`。Ubuntu 26.04 虚拟机，8 vCPU，GCC 15.2，Release `-O3 -DNDEBUG`，性能计时模式 1，逐记录 fsync 审计保留。

本轮环境（2026-10-11）：VMware，客户机显示 i7-13650HX、8 vCPU、1 个 NUMA 节点；内核 7.0.0-38-generic，内存约 7.2 GiB，GCC 15.2.0-16ubuntu1，ext4。客户机显示的拓扑不代表独占宿主机物理核心。

**结论：旧的约 3% P50 上升不足以证明组件改动造成了回归。本轮修复了回报发送要等下一轮推进的问题，但没有测出稳定的整链提速。其余未通过性能筛选的候选已经撤回。**

## 1. 测试时发现了什么

record/06 中，单消费者 peek/pop 每次成本的五轮中位数从 24.846 降至 4.997 ns，池申请/归还从 53.390 降至 18.438 ns。另一次真实网络配对测试中，P50 却从 8.316 变成 8.576 ms，上升约 3.1%。

这两组数测的不是一件事。组件测一次局部操作，整链还包含网络调度、排队和持久审计。仅根据“一处变快、全程变慢”不能确定因果。

同一基线二进制在本轮 50/s 的两次重复运行中，P50 为 9.372 和 9.744 ms，相差约 4%。这说明原 3.1% 差额可能落在环境波动内，但也不能反过来证明所有回归都是噪声，所以继续做分阶段和交替复测。

## 2. 怎样寻找问题

### 持久审计是毫秒级成本

本轮不成交的普通 NEW/CANCEL 各有 RECEIVED、APPLY、RESPONSE 三条持久记录。CriticalJournal 的互斥区包含 write 和 fsync，两个业务线程还会争用同一把锁。

独立插桩诊断记录 1,154 次同步，其中 1,152 次对应 384 条请求的三条记录，另外两次属于文件初始化与目录同步。fsync 耗时中位数约 2.360 ms，累计约 2,993.55 ms。它足以盖过几十纳秒的队列节省，但这不是全部尾延迟的精确因果分解。

将普通文件 fsync 替换为 fdatasync 的诊断没有得到收益：同步中位数约 2.594 ms，整链 P50 从插桩 fsync 的 8.744 变成 9.288 ms。该替换没有进入生产源码。插桩结果只用于诊断，不混入正式性能成绩。

### 回报可能被另一个连接的新请求挡住

旧循环先逐连接执行“发送 + 接收”，再从回报队列取出消息放入 TCP 用户态缓冲。这些回报要等下一轮才真正调用系统 send。

例如 A、B 两个连接：B 的回报已经放进缓冲，下一轮先处理 A；A 在接收回调里做同步审计，就可能推迟 B 的发送。这里的问题是网络循环的工作顺序，不是 TCP 丢了消息。

### 空批次日志多，不等于删掉就会更快

基线一轮只有 384 条实际请求，却产生约 33–36 万条 FIFO 计时记录。原因是 FIFO 内部虽会在空时返回，外层 START/END 仍会计时、格式化和入队。

这在组件优化前后都存在，不能单独用来解释旧 3.1% 差额。实验去掉空批次记录后，OrderServer 日志由约 23–24 MiB 降到约 0.4 MiB，但忙轮询并没有停止，后续交替测试的尾延迟和过载延迟反而变差。因此该候选暂未采用，不能把日志量下降写成已解决整链延迟。

### 测量本身也有边界

部分 TTT 写队列时间点在发布之后，消费者可能先读到并记录时间，直接相减会出现负值。保留负值并说明原因，不截成零；这些时间点只辅助识别大等待，不能冒充精确逐请求因果链。

虚拟机的桌面文件索引服务曾同时运行。后续两组实验在开始前冻结该服务、结束后恢复，双方条件一致；波动仍存在，没有据此把根因全部归给索引服务。没有修改长期服务配置。

## 3. 解决方式与取舍

最终只保留**纯发送刷新**：

1. `TCPSocket::flushSend()` 复用已有短写、EINTR、EAGAIN 和连接错误处理，只发送，不收包、不触发业务回调。
2. `TCPServer::flushSend()` 刷新有待发字节的连接。
3. OrderServer 把完整回报加入 TCP 缓冲后，在当前循环调用纯发送刷新。

序号仍在完整帧入缓冲成功后推进，队列满时保留原回报；不会把 Accepted 解释成对端已经收到。审计、撮合、风控、MODIFY/CANCEL/TRADE 含义均保持原有规则。完整对照见 [修改前后](07_source_changes.md)。

以下候选均已撤回：

| 候选 | 测到的效果 | 最终处理 |
|---|---|---|
| 每连接每轮最多 4 帧 | 过载下回报队列大等待缩短，但整链延迟没有稳定改善 | 不保留接收限额 |
| 空批次不计时 | 日志大幅减少，但交替测试 P99/过载结果恶化 | 不作为默认修复 |
| 连续空闲后睡眠 50 μs | CPU 从约 362% 降到 290%，普通负载 P50 从约 10.044 升至 13.505 ms | 不保留固定睡眠 |
| 空批次 yield | 没有稳定整链收益 | 不保留额外 yield |
| fdatasync 替换 | 独立诊断没有变快 | 保持 fsync |

暂不增加通用自旋锁。审计锁内有磁盘等待，日志锁内可能分配，交易状态锁保护多步一致性，都不能只因 mutex 有开销就替换。

也不直接引入 `std::function<void()>` 通用任务线程。现有 Logger 已后台写文件，前台格式化才是待研究的成本之一。高频诊断可进一步比较“固定大小事件入队，后台格式化”；撮合、风控、确认前持久化与有水位要求的快照不能任意异步化。还必须明确捕获对象生命周期、多个生产者、队列满、异常与停机排空。

### 复测步骤

先保存源码差异与未跟踪文件，分别冻结基线和最终版；不要在同一个构建目录覆盖旧二进制。当前 HEAD 不包含全部工作区修复，源码摘要与修复差异一并归档。

```bash
git rev-parse HEAD
git status --short
cmake -S . -B build/e2e-final -DCMAKE_BUILD_TYPE=Release -DTRADE_PERF_TRACE_EVERY=1
cmake --build build/e2e-final -j4
ctest --test-dir build/e2e-final --output-on-failure
python3 record/07_e2e_latency/run_comparison.py   --baseline /absolute/frozen-before/exchange_main   --final "$PWD/build/e2e-final/exchange_main"   --output /absolute/new-result-directory --rounds 5 --requests 256 --rates 50 500
```

目录必须是新的，脚本不会覆盖旧结果。两边保持审计、日志模式、输入、亲和范围和后台负载相同；本脚本不自动冻结任何桌面服务。检查正确性、窗口内完成比例、排空、P50/P99 和 CPU，不能只截取成功请求的一列延迟。

### 尚未解决

逐记录持久化仍在关键路径；无界接收批次可能拖延回报队列的消费；空批次计时开销仍在；没有完成稳定长期容量和物理网络尾延迟验收。若继续优化，应先改善诊断事件记录与精确阶段计时，再独立设计和验证持久化水位/确认协议，而不是直接取消审计或增加线程。
