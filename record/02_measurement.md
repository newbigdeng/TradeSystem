# 02 测量流程：先把工作量和时间算对

这轮工作先修测量工具，再测交易系统。旧程序给出的“纳秒/次”并不总有正确分母：有的把分配和释放合计时间当一次，有的把订单簿一次调用额外除以 2；日志实验还使用不同输入，只固定等十秒便结束。

## 1. 给每个数字写一句定义

测对象池时，分开记录分配、释放，或明确写“分配释放一对”。测订单簿时，计时前准备输入，计时期间真正执行一次请求，及时消费输出，结束后核对结果。队列满导致提前退出的版本，完成工作量变了，不能继续比较总耗时。

计时采用 `steady_clock` 的纳秒。旧 TSC 值没有完成频率标定，不能直接称为 CPU 周期。CPU 使用率则用同一时间区间的进程累计 CPU 时间差除以墙钟时间差，多线程进程超过 100% 是正常的。

## 2. 生成固定输入，再建立开环请求时间线

历史主批次使用固定种子 20260928、4 客户端、8 品种，NEW:CANCEL 为 1:1，数量 1，价格 100/356/612，构造不成交的新单和成功撤单。每轮先预热，再独立测量。

开环按预定到达时刻提交请求，不等上一条回报。每条保存四个时间：计划发送、第一次写入、完整发送、收到回报。短写继续沿用同一请求身份和进度。

```text
计划发送 ── 生成器迟到/发送进度 ── 完整发送 ── 网络与服务处理 ── 回报到达
|<---------------- 计划发送到回报 -------------------------->|
                                  |<---- 实际发送到回报 ---->|
```

计划到回报反映整个到达计划的服务能力；完整发送到回报更接近客户端实际请求往返。两者都值得记录，名字必须写清。闭环适合检查功能或低在途存储开销，但服务变慢时它会自动少发请求，不能替代固定到达压力。

## 3. 吞吐、积压和分位数一起算

窗口内完成吞吐是“窗口内收到的正式回报数 / 窗口秒数”。窗口结束后回来的请求仍保留完整延迟，但不能补进已经结束的吞吐窗口。积压则看发送、完成之差以及各业务队列随时间的变化。

例如一秒提交 1,000 条，之后八秒才收齐。最终完成 1,000 条说明业务完成了，无法说明服务持续每秒处理 1,000 条。

分位数采用最近秩：排序后取 `ceil(p*n)-1` 下标。每轮单独算 P50/P99，再报告五轮分位数的中位数和范围。五轮各有不同请求，不能把五个 P99 平均后称作总体 P99。

若有超时、未发送或缺回报，先报告数量和截止条件。此时成功样本的 P99 仍可计算，但它只是成功子集；全部请求的精确 P99 可能无法确定。丢掉失败请求会让尾延迟虚假变好。

## 4. 先核对正确性，再解释速度

服务器审计记录 RECEIVED、APPLY 和 RESPONSE。按请求身份核对接收、应用、回报，再检查最终挂单、持仓、队列是否排空。APPLY 是进入处理的记录，不能单凭它推断完整事务已提交。

日志测试要等队列排空后核对文件内容；撮合测试核对全部回报与公开行情；CPU 两次采样要和墙钟分母对齐。曾出现 CPU 分子从发送前开始、分母从计划发送开始的问题，修正后数字变化属于统计修复。

历史主批次 55,000 条正式请求和另一次 CPU 复测的 10,000 条都收到预期回报。业务对账通过，尾延迟门槛没有全部通过。

## 5. 当时测到了什么

环境为 8 vCPU 的 Linux 虚拟机，服务允许 CPU 0–3，生成器用 CPU 4，Release，ext4 上逐条同步审计。下表是五轮“计划发送到回报”P99 的中位数。

| 目标请求/秒 | 正式窗口 | P99，ms | 窗口完成/秒中位数 |
|---:|---:|---:|---:|
| 50 | 20 秒 | 25.251 | 50.0 |
| 100 | 10 秒 | 46.760 | 100.0 |
| 250 | 4 秒 | 4,285.592 | 59.0 |
| 1,000 | 1 秒 | 7,030.902 | 0.0 |

后两档输入速度超过了服务能力，积压把延迟推高。低档也不是五轮全过 20 ms 门槛。

同程序、同输入的闭环存储对照，ext4 P99 为 13.855 ms，tmpfs 为 1.932 ms。这帮助定位同步存储成本；tmpfs 改变了持久性条件，应作为诊断对照。
