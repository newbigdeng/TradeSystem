# 06 整链延迟：把同步落盘、排队和运行环境拆开

组件已经变快，真实请求仍有毫秒甚至秒级延迟。这轮继续追问：时间具体花在哪？代码造成的等待与虚拟机环境波动各占什么证据？本轮以诊断为主，回报优先候选尚未采用。

## 1. 按同一请求拆出三次审计

普通不成交 NEW/CANCEL 会经过 RECEIVED、APPLY、RESPONSE，分别同步 fsync。审计互斥锁还覆盖写入和同步，因此等待可能来自抢锁，也可能来自持有锁期间的存储等待。

给同一请求的锁等待、write、fsync、入队、出队及回报处理分别打点，按请求 ID 关联。不要拿各阶段不同请求的 P50 拼成总耗时。

十轮诊断共 2,560 条正式请求完成逐笔关联。各轮三次 fsync 合计的 P50 约 7.17–8.35 ms，而整链 P50 约 8.31–9.51 ms；锁等待 P50 仅约 0.0006 ms。这里最突出的成本是同步落盘。

同一批样本的平均 fsync 合计 8.054 ms、平均整链 9.304 ms，可算出约 86.6%。使用平均值是因为相同样本可以逐笔求和再求平均；不同阶段的分位数没有这种可加性。

## 2. 解释一条 81 ms 的慢请求

这条请求约 81.02 ms，其中三次 fsync 合计 40.50 ms，持久化完成后的回报等待约 39.98 ms。继续沿线程时间线看，有约 39.44 ms 与接收线程处理另一请求的 RECEIVED 审计重叠。

原因是回报已经准备好，负责收发的线程却先处理新输入并进入同步落盘。上一轮的立即 flush 缩短了回报入缓冲之后的等待；这里讨论的是更早的回报消费调度，两个位置不同。

于是制作候选：处理每个新请求帧前先 `drainResponses()`，让已经准备好的回报先推进。保持请求 FIFO 和确认前审计顺序，验证背压时不提前 pop、不错误推进序号。

确定性反例中，旧顺序失败、候选通过，26 项回归通过；多轮延迟效果却不稳定，所以候选没有采用。结论是找到了一个可重复的调度等待场景，尚未证明该候选在真实负载下有稳定净收益。

## 3. 高负载下主要在哪里积压

500/s 时，RECEIVED 完成到 APPLY 开始的 P50 为 726.58–988.09 ms，而 APPLY 完成到 RESPONSE 开始约 0.07 ms。

前一个区间包含定序、请求队列和线程调度。测到它长，说明请求已经被接收却迟迟轮不到处理；不能把几百毫秒直接称为“队列容器操作耗时”。扩大队列只是允许积压更多，优先要查服务能力和同步处理成本。

## 4. 固定二进制后检查环境

同一正式二进制、50/s，两个批次 P50 出现 973.535 ms 与 37.574 ms，另有预热失败。差异大到不能继续只拿某个代码补丁解释。

虚拟机发现 `localsearch-3.service` 后，保持交易配置不变，进行运行→暂时冻结→恢复的对照，结束时恢复服务。六轮业务均通过：

| 索引服务状态 | 两轮 P50，ms |
|---|---|
| 运行 | 2,231.610 / 1,506.009 |
| 冻结 | 80.818 / 232.464 |
| 恢复 | 976.207 / 854.671 |

冻结时明显改善、恢复后重新变慢，支持索引负载参与了干扰。但冻结后仍有较大延迟，说明它不是已经被证明的唯一原因。

## 5. 交易程序停掉，再测最小存储工作

独立执行 256 次 128 字节 write/fsync，绕开撮合和业务队列。三次条件下的 P99 分别是 83.247、41.326、8.761 ms，仍有明显变化，而且恢复索引服务后的这一轮反而最低。这说明存储环境本身在波动，也提醒我们不能从几轮结果推断一个永久硬件故障。

同时采样 Windows 宿主：213 点 CPU 中位数 18.7%、最大 55.9%，可用内存约 4.88–6.43 GiB，磁盘采样平均写延迟最大 75.8 ms；VM swap 为 0，仍约有 5.7 GiB 可用内存，并出现 I/O 压力。这些支持继续查存储与调度，尚无温度、供电和历史同期数据支持热降频结论。

## 6. 接下来怎样复测才有意义

先记录后台负载、存储位置、CPU 允许范围和持久性配置；用最小 fsync 测试确认环境是否稳定，再交替运行相同二进制检验自然波动，最后比较代码候选。一次只改变一个条件，每次输出到新目录。

这一阶段共 28 次运行：27 次业务通过，1 次基线预热失败。诊断报告对应 `b5eec22`，正式代码仍以已采用的修复为准。
