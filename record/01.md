# 01｜组播接口选择修复：从“订单正常、行情收不到”到增量与快照恢复跑通

日期：2026-09-30

项目：TradeSystem，基于 Packt《Building Low Latency Applications with C++》Chapter12 的学习与改造项目

修复前版本：`ff20fd7`

涉及模块：公共网络工具、组播 Socket、行情发布与订阅链路

本次修复解决了一个容易被“程序能启动”掩盖的问题：交易所和客户端能够通过 TCP 收发订单与成交回报，但客户端没有收到 UDP 组播行情。排查后发现，代码中的 `lo` 配置没有真正用于选择组播网卡，数据实际经过 `ens33`，随后被 UFW 拦截。修复发送接口选择和接收入组接口后，两个客户端都能收到增量行情，晚加入的客户端也完成了快照恢复。

这是一项网络正确性修复。本次没有测量延迟或吞吐提升，不能把“修复后收到了行情”换算成性能提升百分比。

## 一、测试时发现问题：程序启动成功，订单正常，行情却没有到达

### 1. 测试背景

Ubuntu 虚拟机升级后，先检查项目是否仍能编译，再启动交易所和随机客户端验证业务链路。环境如下：

| 项目 | 环境 |
|---|---|
| 操作系统 | Ubuntu 26.04.1 LTS |
| 内核 | 7.0.0-34-generic |
| 编译器 | GCC 15.2.0 |
| 构建工具 | CMake 4.2.3 |
| 构建方式 | Release，保留项目原有的 `-Werror` 等编译选项 |
| 网络 | 同一台虚拟机内运行，配置使用 `lo` 回环接口 |
| 防火墙 | UFW 开启 |

项目声明的最低 CMake 版本是 3.0，而 CMake 4 已移除对这一旧策略版本的兼容。增加 `-DCMAKE_POLICY_VERSION_MINIMUM=3.5` 后，两个主程序和三个 benchmark 都能编译。这个构建兼容问题单独处理，以下重点讨论运行中的行情缺失。

### 2. 原本应当跑通的链路

交易所收到订单后，撮合引擎会产生两类输出：一类是沿 TCP 返回客户端的订单回报，另一类是通过 UDP 组播发布的行情更新。因此，订单回报正常并不自动说明行情也正常。

本机测试中的地址配置是：

| 用途 | 目标地址 | 配置的本地接口 |
|---|---|---|
| 订单与回报 | TCP `127.0.0.1:12345` | `lo` |
| 增量行情 | UDP `233.252.14.3:20001` | `lo` |
| 快照行情 | UDP `233.252.14.1:20000` | `lo` |

`233.252.14.3` 和 `233.252.14.1` 是组播组地址，说明“消息属于哪个组”；`lo` 是本地网络接口，说明“通过哪个接口发送、接收”。这两项配置承担不同职责。

### 3. 实际观察到的异常

启动 `exchange_main` 和 `trading_main 5 RANDOM`，让客户端运行 65 秒后停止本次测试进程。测试期间，两进程存活，TCP 12345 正常监听。客户端网关日志中出现：

| 日志类型 | 修复前记录数 |
|---|---:|
| ACCEPTED，订单被接受 | 911 |
| FILLED，成交回报 | 1,166 |
| CANCELED，撤单成功 | 190 |
| CANCEL_REJECTED，撤单被拒绝 | 720 |
| 行情接收 Socket 的 `read socket` 记录 | **0** |

这些数字是日志行数，不是成交手数，也不是去重后的订单计数。它们用于判断链路是否有活动，不能替代订单数量守恒检查。

异常已经缩小到一个具体方向：订单链路有实际业务回报，客户端行情接收链路没有数据。此时不能只看进程存活，就宣布系统已经跑通。

## 二、寻找问题：沿“有没有发送、走哪张网卡、为什么收不到”逐步排查

### 1. 先检查发送端有没有产生行情

交易所的行情发布日志持续出现增量序号和发送记录，检查到的发送日志没有 `len:-1`。这说明撮合后的行情已经到达发布模块，也已经交给 Socket 发送。

不过，发送调用成功只能说明内核接受了发送请求，不能证明接收端已经收到报文。因此，下一步检查报文实际经过的接口。

### 2. 检查系统对组播目标的路由选择

执行：

```bash
ip route get 233.252.14.3
```

结果显示目标走的是 `ens33`，源地址为 `192.168.29.128`。这与程序配置的 `lo` 不一致。

随后检查内核日志，发现明确的拦截记录：

```text
[UFW BLOCK] IN=ens33 SRC=192.168.29.128 DST=233.252.14.3 ... PROTO=UDP ... DPT=20001
```

这条日志解释了现象：行情包实际进入 `ens33` 的接收路径，被防火墙拦截，所以客户端一直收不到行情。

### 3. 用独立的小测试确认接口选择的影响

为了把“应用代码问题”和“系统无法收发组播”分开，使用独立 UDP 组播探针，向同一个组地址发送一条短消息，仅改变本地接口：

| 探针设置 | 结果 |
|---|---|
| 不指定接口，交给系统选择 | 接收超时 |
| 显式指定 `192.168.29.128`，对应 `ens33` | 接收超时 |
| 显式指定 `127.0.0.1`，对应 `lo` | 成功收到原消息 |

这表明，本机回环接口上的组播收发是可用的，关键是程序必须把接口配置真正传给内核。

### 4. 回到源码，找到配置失效的位置

问题涉及三处代码，以下展示的是修复前实现。

**第一处：[`common/socket_utils.h`](../common/socket_utils.h) 的 `createSocket()`。**

```cpp
const auto ip = socket_cfg.ip_.empty()
    ? getIfaceIP(socket_cfg.iface_)
    : socket_cfg.ip_;
```

只有目标 IP 为空时，这段代码才读取接口 IP。行情 Socket 已经提供了组播目标地址，所以表达式直接使用目标地址，`iface_` 没有参与组播发送接口选择。其余创建 Socket 的代码也没有设置 `IP_MULTICAST_IF`，最终由系统路由选择发送网卡。

因此，配置中写了 `lo`，并不代表组播实际从 `lo` 发出。

**第二处：同文件中的 `join()`。**

```cpp
const ip_mreq mreq{
    {inet_addr(ip.c_str())},
    {htonl(INADDR_ANY)}
};
setsockopt(fd, IPPROTO_IP, IP_ADD_MEMBERSHIP, &mreq, sizeof(mreq));
```

`imr_multiaddr` 指定要加入的组；`imr_interface` 指定在哪个接口加入。旧代码把接口字段设为 `INADDR_ANY`，把入组接口的选择也交给了系统，没有使用应用配置中的 `lo`。

**第三处：[`common/mcast_socket.cpp`](../common/mcast_socket.cpp) 的 `McastSocket::join()`。**

```cpp
return Common::join(socket_fd_, ip);
```

`McastSocket::init()` 虽然收到了接口名，但对象没有保存它，后续入组时也无法把接口名传下去。这个问题同时影响初始增量订阅和检测到缺口后启动的快照订阅。

最终定位到的原因是：**发送端缺少组播接口设置，接收端缺少明确的入组接口，且中间封装没有传递接口配置。** 防火墙拦截是这次环境中暴露问题的直接现象，修复应落在接口配置的完整传递上。

## 三、解决问题：让发送和接收都使用配置中的接口

### 1. 发送端：在连接目标前设置组播发送接口

在 `createSocket()` 中，识别“UDP、发送端、目标地址属于 IPv4 组播”这一情况，再把配置接口的 IPv4 地址写入 `IP_MULTICAST_IF`：

```cpp
const auto iface_ip = getIfaceIP(socket_cfg.iface_);
ASSERT(!iface_ip.empty(),
       "No IPv4 address for multicast interface: " + socket_cfg.iface_);

in_addr iface_addr{};
ASSERT(inet_pton(AF_INET, iface_ip.c_str(), &iface_addr) == 1,
       "Invalid multicast interface address: " + iface_ip);

ASSERT(setsockopt(socket_fd, IPPROTO_IP, IP_MULTICAST_IF,
                  &iface_addr, sizeof(iface_addr)) == 0,
       "setsockopt() IP_MULTICAST_IF failed. errno:" +
           std::string(strerror(errno)));
```

这项设置放在 `connect()` 之前，使 Socket 在连接组播目标前已经确定发送接口。当前配置为 `lo`，查出的地址就是 `127.0.0.1`。TCP 和普通单播 UDP 不进入这段组播设置逻辑。

### 2. 接收端：按指定接口加入组播组

把工具函数签名改为：

```cpp
join(int fd, const std::string &ip, const std::string &iface)
```

读取配置接口的 IPv4 地址，将其写入 `ip_mreq.imr_interface`，再执行 `IP_ADD_MEMBERSHIP`。接收端现在明确在 `lo` 上加入相应的组，而不是让路由决定入组接口。

同时补充输入检查：接口不存在或没有 IPv4 地址时，返回 `false` 并设置 `ENODEV`；目标不是有效 IPv4 组播地址时，返回 `false` 并设置 `EINVAL`。发送端遇到无效接口则按项目现有的 `ASSERT` 方式明确退出。这避免了错误配置被静默转换为默认接口。

### 3. Socket 封装：保存接口名，贯穿增量和快照订阅

在 [`common/mcast_socket.h`](../common/mcast_socket.h) 中增加 `iface_`。在 `init()` 中保存接口名，在 `join()` 中传递它：

```cpp
// McastSocket::init()
iface_ = iface;

// McastSocket::join()
return Common::join(socket_fd_, ip, iface_);
```

这使增量接收 Socket 和后来初始化的快照接收 Socket 都遵循同一接口配置。

### 4. 增加自动化回归测试

新增 [`tests/multicast_interface_test.cpp`](../tests/multicast_interface_test.cpp)，并在 [`CMakeLists.txt`](../CMakeLists.txt) 注册两项 CTest：

| 测试 | 验证内容 |
|---|---|
| `multicast_interface` | 分别对增量组和快照组使用临时端口，检查发送接口确实是 `127.0.0.1`，并验证接收到了完整原消息；同时检查错误接口和非组播地址的入组失败路径 |
| `multicast_invalid_interface` | 指定不存在的发送接口，验证初始化明确失败 |

第一项测试既检查内核 Socket 选项，也检查真实报文收发，避免“代码调用了设置函数，但链路仍不可用”的情况。第二项测试通过 CTest 的 `WILL_FAIL` 配置验证预期的非零退出。

本次修复保持 UFW 开启，没有依靠关闭防火墙或改系统路由来使测试通过。

## 四、重新测试：验证增量行情，并让晚加入客户端走完快照恢复

### 1. 编译和自动化回归

在项目根目录执行：

```bash
cmake -S . -B build/multicast-interface-release \
  -DCMAKE_BUILD_TYPE=Release \
  -DCMAKE_POLICY_VERSION_MINIMUM=3.5
cmake --build build/multicast-interface-release -j2
ctest --test-dir build/multicast-interface-release --output-on-failure
```

`build/` 已在项目 `.gitignore` 中。CMake 兼容参数用于这次 Ubuntu 26.04 的 CMake 4 环境，本次没有改动项目原有的最低版本声明。

首次修复后的结果是：编译成功，CTest **2/2 通过**。

整理报告、准备提交时，又在上面的持久构建目录中全新编译了所有目标，并重新运行 CTest：**2/2 通过，0 项失败**。这次提交前的测试日志位于 `build/multicast-interface-release/ctest.log`。原始构建日志按 `.gitignore` 留在本机，本报告和回归测试源码随修复一并提交。

### 2. 双客户端业务测试

自动化回归通过后，继续使用主程序验证业务链路：

1. 启动交易所，确认 TCP 12345 已经监听。
2. 启动随机客户端 5，让交易所先产生一段连续行情。
3. 38 秒后启动随机客户端 6。它错过了前面的增量序号，会检测到缺口，进入快照恢复。
4. 继续观察 60 秒，检查两客户端的行情和订单回报，并检查客户端 6 的快照恢复日志。
5. 测试结束时，仅向本次启动的进程发送 SIGTERM。

晚加入客户端的设计同时覆盖了两个组播组：如果只验证第一个客户端收到了增量行情，仍无法证明快照订阅也选对了接口。

下面是 2026-09-30 首次修复后业务测试保存于本地修复记录中的结果：

| 日志观测项 | 客户端 5 | 晚加入的客户端 6 |
|---|---:|---:|
| 收到增量行情记录 | 6,422 | 4,839 |
| 收到快照消息记录 | 0，未触发恢复 | 134 |
| ACCEPTED 回报记录 | 1,915 | 911 |
| FILLED 回报记录 | 2,871 | 1,287 |

客户端 6 出现以下恢复日志：

```text
Recovered 132 snapshot and 16 incremental orders.
```

134 条快照消息包含开始和结束标记，日志中的 132 条是扣除这两条标记后的快照记录。接收端完成快照和后续增量的拼接，退出恢复状态，并继续接收增量行情。

测试期间三个进程存活；系统组播成员表显示增量组的两名订阅者在 `lo`；对应测试时间段内，两行情组地址的新增 `UFW BLOCK` 记录为 0。

### 3. 修复前后对比

| 检查点 | 修复前 | 修复后 |
|---|---|---|
| 发送接口 | 没有显式设置，实际走 `ens33` | 按配置明确使用 `lo` |
| 接收入组接口 | `INADDR_ANY`，由系统选择 | 按配置在 `lo` 上入组 |
| 客户端增量行情 | 未收到，接收日志为 0 | 两客户端均收到 |
| 晚加入后的快照恢复 | 行情链路阻塞，无法完成本次验收 | 收到完整快照并完成恢复 |
| UFW | 开启，记录了组播拦截 | 保持开启，测试期间无相关新增拦截 |

修复前后使用的客户端数量、持续时间不同，因此日志数量只用于判断业务链路是否恢复，不用于比较吞吐或延迟。

### 4. 数据来源和验收范围

修复前的日志计数、组播探针和 UFW 拦截记录已保存到本地检查记录。首次修复后的端到端数据来自当时测试完成后保存的修复报告；原 `/tmp` 原始日志在本次整理报告时已被清理。本报告保留这组历史数据，并在提交前补做当前代码的编译与回归验证，不把历史计数写成新一轮测试结果。

本次证明了配置接口能够控制组播收发，且主程序的增量行情和晚加入快照恢复链路能运行。测试是有时限的业务冒烟，尚未覆盖完整 10,000 轮随机负载、撮合数量守恒、中心订单簿与客户端订单簿的全量对账，以及优雅退出。也没有升级前相同网络条件下的对照测试，因此不能断言这个代码问题由系统升级新引入。

以后修改组播封装或网络接口配置时，可先运行这两项 CTest，再用晚加入客户端验证快照恢复，避免只检查订单 TCP 链路而漏掉行情链路。
