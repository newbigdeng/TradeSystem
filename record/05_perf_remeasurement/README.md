## 2. 实际 perf 操作和发现

原 `kernel.perf_event_paranoid=4` 阻止普通用户采集，本次临时设为1。软件事件探针成功；cycles/instructions 硬件探针仍不可用，见成功的软件探针（离线证据包：`evidence/software_probe.txt`）和硬件事件失败记录（离线证据包：`evidence/hardware_probe.txt`）。权限与虚拟机 PMU 支持分别验证，没有伪造 IPC 或 cache-miss 数据。

```bash
perf stat -e task-clock,context-switches,cpu-migrations,page-faults -- sleep 0.2
perf stat -e cycles:u,instructions:u -- sleep 0.2

# 附加到驱动自己启动的服务；预热8秒，随后100/s测24秒。
perf stat -x ';' -e task-clock,context-switches,cpu-migrations,page-faults \
  -o perf_stat.txt -p "$SERVER_PID"
perf record -e cpu-clock:u -F 99 --call-graph fp -o perf.data -p "$SERVER_PID"
# 驱动在测量结束后给这两个perf进程SIGINT，并检查计数与profile是否真正生成。
perf report --stdio --no-children --percent-limit 0.5 -i perf.data
perf report --stdio --children --percent-limit 1 -i perf.data
perf annotate --stdio --source --symbol='Exchange::MatchingEngine::run()' -i perf.data
```

服务采样共 **5,111 样本，Total Lost Samples=0**。软件 stat：task-clock **82,705.87 ms**、context-switches **147,840**、cpu-migrations **1,342**、page-faults **1,088**。task-clock是所有线程累计CPU时间，超过约24秒观测墙钟不表示计时出错；软件计数覆盖用户态/内核态，而采样限定用户态，不能直接拿二者相减当精确内核耗时。

Self：`__syscall_cancel_arch_end`约26.37%，一个vDSO时钟路径约24.54%，`MatchingEngine::run()`约21.91%。调用树中`system_clock::now()`的Children约39.89%。不同统计范围不能相加。`perf annotate`将撮合循环的采样集中指向运行标记、head/tail读取比较与回跳；源码在空队列时持续轮询，与观察一致。

这证明了**CPU热点**，没有证明全部P99毛刺的根因。线程睡眠等待fsync时可能不出现在用户态CPU采样中，vDSO与系统库的符号/帧指针也有边界。忙轮询和频繁读时钟可作为后续干预对象；本次没有把修改它们后的收益写成已完成。

证据：stat（离线证据包：`evidence/exchange_perf_stat.txt`）、Self报告（离线证据包：`evidence/exchange_perf_report.txt`）、调用树（离线证据包：`evidence/exchange_perf_callgraph.txt`）、采样记录（离线证据包：`evidence/exchange_perf_record_stderr.txt`）、撮合指令注释（离线证据包：`evidence/perf_annotate_matching.txt`）、快照指令注释（离线证据包：`evidence/perf_annotate_snapshot.txt`）。原始perf.data在诊断数据包（离线证据包：`network/perf_b1_r100.tar.gz`）内；其他机器解析需匹配build-id的二进制，原VM保留构建。官方用法参考[perf record](https://man7.org/linux/man-pages/man1/perf-record.1.html)与[perf权限接口](https://man7.org/linux/man-pages/man2/perf_event_open.2.html)。

## 3. 双线程组件单因素实验

24字节消息、容量1024，每个配置五轮，每轮独立10万条CPU预热、正式200万条传输。正式进程先做满/空/回绕校验；所有消息检查序号与内容。吞吐定时包含共同的1/64时间戳采样；P99仅为抽样的“首次尝试入队前→取出”，包括重试、组批与积压，不是完整业务延迟或全量消息P99。固定采样相位可能漏掉周期性毛刺。

- `aligned`：当前64字节分隔head/tail、取模、单条try_push。
- `packed`：只移除head/tail的alignas(64)；实际地址观测五轮均处于同一64字节行，其他变体均分离。
- `mask`：只将槽位取模改为二次幂掩码；容量合同收紧，容量0/3显式拒绝，不能全局直接替换。
- `batch1/8/32`：使用相同try_push_batch接口，改变批量；与普通try_push的aligned不是同一调用路径。

| 组件配置 | 吞吐中位数 M msg/s | 五轮吞吐 M msg/s | 抽样 P99 中位数 μs |
|---|---:|---|---:|
| aligned | 14.3424 | 12.677 / 13.240 / 15.040 / 14.342 / 14.919 | 93.836 |
| packed | 11.7427 | 15.001 / 8.795 / 12.749 / 11.743 / 11.143 | 168.524 |
| mask | 16.2987 | 15.480 / 17.424 / 16.330 / 16.299 / 15.262 | 95.506 |
| batch1 | 9.5050 | 9.505 / 10.390 / 9.514 / 9.337 / 9.444 | 107.408 |
| batch8 | 25.8286 | 24.998 / 27.807 / 25.829 / 29.238 / 25.536 | 91.223 |
| batch32 | 38.2237 | 38.224 / 38.088 / 43.050 / 39.726 / 33.498 | 73.575 |

正式合计**6000万条传输全部正确**。同轮吞吐增幅中位数：packed→aligned **22.14%**，aligned→mask **13.64%**，batch1→batch8 **170.39%**，batch1→batch32 **302.14%**。这些是不同对照，不能累加；302.14%的基准是批量接口的一条发布，不是原单条try_push，更不是交易系统吞吐。

packed第一轮更快，其余轮次相反；完整数据仍保留。没有硬件一致性计数时，不能把布局总效果精确分解为cache-miss或伪共享流量。没有测完整的布局×批量交互矩阵。原始五轮见queue_runs（离线证据包：`evidence/queue_runs.json`），队列的真实perf诊断分别见[evidence目录](evidence)。

## 4. 真实请求链路的批处理比较

每组五轮，30秒同速预热+60秒观察，100请求/秒、每轮6000正式请求；共**90,000正式请求/含预热135,000请求**。15轮全部正确对账。FIFO只合并已到达请求，不等待凑批；整批空间不足时逐条推进并保留剩余后缀。三个变体使用同一实验实现，只改变批量上限，控制组batch1同样使用vector/批量接口，因此这不是未修改生产FIFO与候选的完整前后对比。

## 8. 可以据此表述什么？

可以说已使用Linux perf分析CPU热点，完成队列索引、缓存布局和批量发布的独立对照，搭建开环负载与逐轮业务核验；在指定条件下50/s五轮P99中位**15,649 μs**，追加304秒P99 **18,156 μs**。

不能说组件3822万消息/s就是完整交易系统吞吐，不能说batch32改善了业务P99，也不能说已经测出生产最大稳定容量、硬件cache-miss、IPC或全部慢请求的off-CPU根因。旧record/03的96.28%是另一组诊断日志策略的逐轮配对降幅，不是本次批处理收益。
